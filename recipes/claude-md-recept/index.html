Большинство файлов с правилами для агента выглядят как список пожеланий: «пиши чистый код», «следуй best practices», «не делай ошибок». Модель читает это, кивает и делает по-своему. Потому что пожелания нельзя проверить.

Рабочий CLAUDE.md — не промпт. Это контракт: короткий, проверяемый, с границами. Ниже — структура из семи секций, которая пережила четыре проекта и пару смены модели.

Почему это не промпт

Промпт живёт один запрос. Файл правил живёт месяцы и читается на каждом шаге. У них разные задачи:

Промпт Файл правил
получить конкретный результат удержать поведение
можно импровизировать должен быть скучным
1 запрос каждый шаг агента
меняется под задачу меняется раз в квартал

Чем чаще файл меняется, тем хуже он работает. Если вы правите правила каждый день — вы лечите симптом, а не процесс.

Скелет файла

Держите его в корне репозитория и коммитьте вместе с кодом. Не в личных настройках редактора: правила — часть проекта.

# Project: checkout-service

## 1. Что это
Платёжный сервис. Node 22, Fastify, Postgres, Zod.
Прод — k8s, стейджинг — fly.io.

## 2. Команды
- dev:      pnpm dev
- test:     pnpm test -- --run
- typecheck: pnpm tsc --noEmit
- lint:     pnpm lint --fix

## 3. Границы
- НЕ трогай migrations/ — только через `pnpm db:new`
- НЕ меняй публичные схемы без обновления OpenAPI
- Секреты только через env, никогда в коде

## 4. Стиль
- Ошибки: Result<T, E>, не throw на границах
- Логи: pino, структурные, без PII
- Тесты: рядом с модулем, имя = поведение

## 5. Процесс
1. Прочитай задачу и перескажи её одним абзацем
2. Предложи план: файлы + риски
3. Жди подтверждения
4. Код → тесты → typecheck
5. Отчёт: что изменил, что не проверено

## 6. Запрещено
- Массовые рефакторинги без отдельной задачи
- Новые зависимости без обоснования
- `any`, `@ts-ignore`, `eslint-disable` без комментария

## 7. Definition of done
- [ ] тесты зелёные
- [ ] typecheck чистый
- [ ] нет новых warning в логе
- [ ] diff < 300 строк, иначе — план

Семь секций, по одной на вопрос

Каждая секция отвечает на вопрос, который агент всё равно задаст — только позже и дороже.

  1. Что это. Стек и контекст. Без этого модель выбирает паттерны из чужих проектов.
  2. Команды. Точные, копируемые. Не «запусти тесты», а конкретная строка.
  3. Границы. Что нельзя трогать. Самый недооценённый раздел.
  4. Стиль. Только то, что отличается от дефолта модели. Не пересказывайте Airbnb style guide.
  5. Процесс. Порядок шагов. Здесь живёт «сначала план».
  6. Запреты. Антипаттерны, которые уже случались. Список растёт, но медленно.
  7. Definition of done. Проверяемый результат. Агент любит закрывать задачи; дайте ему критерий закрытия.

Правило одной строки. Если правило нельзя проверить командой или глазами за 10 секунд — это не правило, а пожелание. Переписывайте или выбрасывайте.

Тест на качество

Возьмите свежий чат, дайте агенту файл и попросите: «перечисли, что ты понял, и задай вопросы». Хороший файл даёт 2–3 уточняющих вопроса про задачу. Плохой — вопросы про очевидное: где код, как запускать, что считается готовым.

Второй тест: уберите любую секцию и запустите типичную задачу. Если поведение не изменилось — секция была декоративной.

Чего не делать

  • Не дублировать README. README — для людей. Файл правил — для агента. Пересечение допустимо, копипаст — нет.
  • Не писать «будь аккуратным». Аккуратность не измеряется.
  • Не хранить больше 150 строк. После этого файл перестают читать — и люди, и модели.
  • Не добавлять правило без случая. Каждый пункт — это чей-то реальный инцидент, а не теория.

Мини-рецепт: скопируйте скелет выше, замените команды и границы на свои, удалите всё, что не относится к вашему стеку. Первая версия — 20 строк. Дальше добавляйте только после провала.

Чек-лист

  • файл лежит в корне и в git
  • все команды скопированы из реального терминала
  • есть минимум одна жёсткая граница
  • процесс содержит шаг «план до кода»
  • definition of done проверяется, а не обсуждается
  • файл короче 150 строк

Дальше — самое сложное: не трогать его неделю. Если за неделю появилось желание дописать десять правил, скорее всего, проблема не в файле, а в постановке задач.
