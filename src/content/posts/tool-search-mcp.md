Если нужна только инструкция «включить и проверить» — она в [рецепте на пять минут](/concepts/tool-search-5-minut). Здесь — как механизм устроен, где проходит граница экономии и почему поиск иногда не находит нужную ручку.

## Коротко

- Пять MCP-серверов могут занимать **55K токенов** до первого вопроса.
- Tool Search оставляет в контексте один поисковик на **~500 токенов** и подгружает **3–5 инструментов** по запросу.
- В замере из выпуска пик — **2,5K токенов** вместо 55K.
- Экономия касается **схем**, а не ответов инструментов: 40K лог всё ещё может прилететь.

## Что происходит без Tool Search

MCP-клиент при старте отправляет модели описания всех инструментов. Не потому что они нужны, а потому что так устроен протокол: модель должна знать, что вообще доступно.

| Сервер | Схемы | Токены |
| --- | ---: | ---: |
| GitHub | 20 | 14K |
| Slack | 16 | 21K |
| Sentry | 9 | 8K |
| Grafana | 7 | 7K |
| Splunk | 6 | 5K |
| **Итого** | **58** | **55K** |

55K из 200K — это **27,5%** окна. Четверть контекста уходит на меню инструментов, которыми в конкретной задаче ты можешь не воспользоваться ни разу.

## Как работает Tool Search

1. Клиент получает от MCP-серверов все 58 схем.
2. Вместо них в контекст кладётся один инструмент поиска — около 500 токенов.
3. Модель формулирует запрос: `github actions build`.
4. Поисковик возвращает ссылки на подходящие инструменты.
5. Клиент разворачивает их в полные определения и кладёт в контекст.
6. Модель вызывает найденную ручку.

В примере из выпуска находятся три инструмента GitHub, а `find_releases` из Sentry остаётся за стеклом. В контекст попадает `actions_list` — точное действие, которое нужно для проверки последнего билда.

Важно: **все определения по-прежнему уходят в запросе**. `defer_loading` управляет не размером запроса, а тем, что попадает в контекст модели. API нужно знать о инструментах, чтобы искать по ним.

## Цена и границы

| Состояние | Токены в контексте |
| --- | ---: |
| Все схемы сразу | 55K |
| Старт с поисковиком | ~0,5K |
| Поиск + найденные инструменты | ~2,5K пик |

Цифры — замер на пяти конкретных серверах, а не универсальная константа. Если у тебя 10 серверов и 300 инструментов, абсолютные значения будут другими. Но направление то же: контекст платит за описания, а не за возможности.

## Свой агент на API

В Anthropic Messages API есть два варианта поисковика:

| Тип | Когда использовать |
| --- | --- |
| `tool_search_tool_regex_20251119` | Точные имена, префиксы, шаблоны |
| `tool_search_tool_bm25_20251119` | Естественный язык: «найди инструмент для проверки билда» |

Минимальная схема:

```json
{
  "tools": [
    {
      "type": "tool_search_tool_regex_20251119",
      "name": "tool_search_tool_regex"
    },
    {
      "name": "github_actions_list",
      "description": "List GitHub Actions workflow runs for a repository",
      "input_schema": {
        "type": "object",
        "properties": {
          "owner": { "type": "string" },
          "repo": { "type": "string" }
        },
        "required": ["owner", "repo"]
      },
      "defer_loading": true
    }
  ]
}
```

Правила:

- **Не откладывай поисковик.** Он должен быть доступен с первого шага.
- **Оставь 3–5 частых инструментов non-deferred.** Иначе модель будет искать даже то, что вызывает постоянно.
- **Все определения отправляй в запросе.** Иначе API не сможет развернуть `tool_reference`.
- **Не откладывай всё подряд.** Если все инструменты спрятаны, модель тратит лишний шаг на поиск и может не найти нужное.
- **Проверяй лимиты.** По умолчанию поиск возвращает до 5 совпадений; лимит можно поднять в запросе. Отложенных инструментов — до 10 000 на запрос.
- **Regex — до 200 символов, BM25 — до 500.** Это ограничения поискового запроса, а не описания инструмента.

Для MCP-сервера целиком удобно откладывать весь набор и точечно оставлять частые ручки:

```json
{
  "type": "mcp_toolset",
  "mcp_server_name": "github",
  "default_config": { "defer_loading": true },
  "configs": {
    "actions_list": { "defer_loading": false }
  }
}
```

## Почему поиск промахивается

Поиск смотрит на имена, описания и аргументы инструментов. Но на практике решает короткое человеческое описание.

Работает:

```text
actions_list — List GitHub Actions workflow runs for a repository
```

Не работает:

```text
do_action — v2 helper tool
```

Второе имя не говорит ни что делает инструмент, ни где он применяется. Модель не обязана угадывать по названию сервера.

Правила нейминга:

- **Глагол + объект:** `actions_list`, `issues_search`, `logs_tail`.
- **Уникальность:** не называй два инструмента `find_releases`, если они из разных серверов.
- **Ключевые слова в описании:** `GitHub`, `Actions`, `workflow`, `build`, `CI`.
- **Аргументы со смыслом:** `owner`, `repo`, `workflow_id` лучше, чем `a`, `id`, `param`.
- **Проверка запросом:** попроси модель найти инструмент так, как это сделал бы человек, и посмотри, что вернёт поиск.

## Грабли

**Нет поддержки.** На старых моделях и в облаках без механизма клиент загружает схемы сразу. Это fallback, а не ошибка конфигурации.

**Поисковик отложен.** Модель не может искать тем, чего нет в контексте.

**Все инструменты отложены.** Экономия есть, но каждый шаг начинается с поиска. Оставь 3–5 основных ручек.

**Токены не падают.** Проверь, что клиент поддерживает `defer_loading`, что ты измеряешь контекст, а не размер запроса, и что схемы не продублированы в системном промпте.

**Поиск не находит инструмент.** Смотри имя, описание, аргументы и лимит выдачи. Иногда помогает BM25 вместо regex.

**Ответ инструмента всё равно огромный.** Tool Search экономит схемы, но не ответы. Лог на 40K токенов после успешного поиска всё ещё займёт контекст. Это следующая задача — [изоляция и сжатие результатов](/concepts/anthropic-code-execution).

**Кэш.** Отложенные определения не входят в начальный промпт, поэтому системный промпт и основные инструменты могут оставаться кэшируемыми. Но не ставь `cache_control` на отложенный тулсет: его содержимое не входит в кэшируемый префикс.

## Чек-лист

- [ ] поисковик не отложен;
- [ ] 3–5 частых инструментов загружены сразу;
- [ ] все определения отправляются в запросе;
- [ ] имена и описания уникальны и описывают действие;
- [ ] замер до/после показывает падение контекста, а не только размера запроса;
- [ ] проверен fallback на моделях и в облаке;
- [ ] есть план на случай огромного ответа инструмента.

## Готовые клиенты

- **Claude Code.** Tool Search уже включён по умолчанию; поведением управляет `ENABLE_TOOL_SEARCH` (`true`, `auto`, `auto:N`, `false`). Короткая инструкция — в [рецепте](/concepts/tool-search-5-minut).
- **Cursor.** Динамическая подгрузка схем встроена; отдельный флаг не нужен.

## Частые вопросы

**Tool Search включён по умолчанию?**  
В Claude Code — да, в текущих версиях; поведением управляет `ENABLE_TOOL_SEARCH`. В API его нужно добавить в `tools` явно.

**Сколько токенов он экономит?**  
В замере из выпуска — 55K → 0,5K на старте и около 2,5K в пике. Зависит от количества серверов, инструментов и длины описаний.

**Почему не находится нужный инструмент?**  
Чаще всего из-за имени и описания. Поиск идёт по именам, описаниям и аргументам, но `do_action` с описанием «v2 helper tool» не даёт зацепок. Проверь также, что поисковик не отложен и что лимит выдачи не слишком мал.

**Работает ли это в Cursor?**  
Динамическая подгрузка там встроена; отдельный флаг не нужен. Проверь подключение MCP-серверов и версию клиента.
