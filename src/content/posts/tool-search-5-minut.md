## Что это даёт

- **Старт дешевле:** ~0,5K токенов на поисковик вместо 55K на описания пяти MCP-серверов.
- **В контексте только нужное:** модель ищет инструмент и получает 3–5 ручек, а не все 58.
- **Пик около 2,5K** вместо 55K — на том же наборе серверов. Абсолютные цифры зависят от описаний.
- **Меняется контекст, а не запрос:** все определения по-прежнему уходят в API; `defer_loading` решает, что попадёт в промпт.

## Что понадобится

- ключ Anthropic API и модель с поддержкой tool search;
- полные определения всех инструментов;
- 3–5 самых частых инструментов, которые останутся загруженными сразу;
- один поисковик: regex-вариант для точных имён или BM25 для естественных запросов.

## Шаги

### 1. Добавь поисковик

Он должен быть доступен с первого шага, поэтому **не** помечай его `defer_loading`.

```json
{
  "type": "tool_search_tool_regex_20251119",
  "name": "tool_search_tool_regex"
}
```

Для запросов вида «найди инструмент для проверки билда» возьми `tool_search_tool_bm25_20251119`.

### 2. Оставь 3–5 частых инструментов загруженными

Их не нужно искать на каждом шаге. Всё остальное можно отложить.

```json
{
  "name": "github_actions_list",
  "description": "List GitHub Actions workflow runs for a repository",
  "input_schema": {
    "type": "object",
    "properties": {
      "owner": { "type": "string" },
      "repo": { "type": "string" }
    },
    "required": ["owner", "repo"]
  },
  "defer_loading": true
}
```

`defer_loading` не уменьшает запрос. Он убирает определение из контекста, пока инструмент не найден.

### 3. Отправляй все определения

API нужно знать о каждом инструменте, чтобы искать по каталогу и разворачивать найденные ссылки в полные схемы. Не пытайся отправлять только незагруженные.

### 4. Для MCP-сервера целиком

Если сервер отдаёт много ручек, отложи весь набор и оставь частные исключения:

```json
{
  "type": "mcp_toolset",
  "mcp_server_name": "github",
  "default_config": { "defer_loading": true },
  "configs": {
    "actions_list": { "defer_loading": false }
  }
}
```

### 5. Проверь на реальной задаче

Запрос «проверь последний билд» должен привести к `actions_list`, а не к похожему `find_releases` из другого сервера. Если поиск уходит не туда — смотри имена и описания, а не модель.

## Проверка

- [ ] поисковик не отложен;
- [ ] 3–5 частых инструментов загружены сразу;
- [ ] все определения отправляются в запросе;
- [ ] имена и описания уникальны и описывают действие;
- [ ] до первого вопроса в контексте нет 50K токенов схем;
- [ ] после поиска в контексте появляются только нужные инструменты;
- [ ] замеряешь контекст, а не размер запроса.

## Если не получилось

**Инструмент не находится.** Проверь имя, описание, аргументы и лимит выдачи. `do_action` с описанием «v2 helper tool» не даёт поиску зацепок.

**Токены не падают.** Убедись, что клиент поддерживает `defer_loading`, что схемы не продублированы в системном промпте и что ты измеряешь контекст.

**Всё сломалось на старой модели.** На моделях и в облаках без поддержки механизма клиент загружает схемы сразу. Это fallback, а не ошибка конфигурации.

**Ответ инструмента всё равно огромный.** Tool Search экономит схемы, но не ответы. Лог на 40K токенов после успешного поиска всё ещё займёт контекст.

## Готовые клиенты

- **Claude Code.** Tool Search уже включён по умолчанию; поведением управляет `ENABLE_TOOL_SEARCH` (`true`, `auto`, `auto:N`, `false`).
- **Cursor.** Динамическая подгрузка схем встроена, отдельный флаг не нужен.
